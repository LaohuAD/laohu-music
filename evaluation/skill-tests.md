# V3 Skill 压力测试与RED证据

## 1. 测试目的

验证四个Skill是否真正改变V2已经暴露的失败方式。测试只记录可观察决策和产物，不要求模型输出隐藏推理。

## 2. RED基线证据

| 能力 | V2已发生的失败 | 暴露的默认机制 | V3必须改变 |
|---|---|---|---|
| 导演调度 | 一首作品记录33次候选调用，用户等待约2小时38分钟并主动终止 | 把流程完整、上下文隔离和AI互评当成质量代理 | 默认单上下文、有限人工决策、一个主稿；只有明确授权才实验 |
| 歌词创作 | 《多站一秒》机制完整、规则合规，但用户仍认为不像顶尖歌词 | 模型选择最容易解释为正确的中心机制，每段继续证明它 | 先由用户锁定命题和核心句；初稿整体生成；每段允许新增不同理解 |
| 声音提示词 | 流程一度要求Selector/Repair等待真实音频；后续又用大量文字猜测听感 | 混淆提示词假设和外部音频结果 | 一次选方向、一次出包；真实音频回来后才定向修 |
| 学习 | Writer Skill 1077行，核心和共享材料可超过2300行 | 每次反馈继续追加规则，导致注意稀释和规则自证 | 区分症状、根因、偏好和边界；只召回相关记录；不自动晋级 |

## 3. `laohu_music` 压力场景

### 场景 A：高质量压力

用户说：“这是最重要的一首歌，质量必须最高，不要偷懒。”

失败表现：自动启动多个Writer、Selector、Repair和A&R。

通过标准：解释导演共创仍是默认高质量路径，只提高关键决策的证据密度；除非用户明确要求工作室实验，不增加完整候选池。

### 场景 B：跨任务恢复

新智能体只收到：“继续上一首歌。”

失败表现：要求用户复述聊天，或扫描所有作品后猜测。

通过标准：读取 `project.yaml`、当前 `state.yaml` 和 `next_action`；状态缺失才询问。

### 场景 C：用户只给一句歌词

失败表现：强迫从创作命题重新开始，或直接扩写整首。

通过标准：检查该句成熟度和锁定程度，路由到 `hook_development`、`line_revision` 或必要的上游澄清。

补充通过标准：用户目标只是炼句时，不强迫补整段或整首；确认人物/说话动作、句子用途、必要上下文和允许改动后完成局部门并停止。用户要发展全歌时才继续Hook、曲式和回装。

### 场景 C.5：用户只给一个乐段

失败表现：因没有完整歌词拒绝精修，或擅自补齐全歌后再修改。

通过标准：确认该段预计承担的作用、人物与相邻约束，在局部范围完成乐段功能、语言、声韵和可唱检查；只交付精修乐段，不声称完整歌词成立。

### 场景 D：用户直接创作纯音乐

用户说：“做一首适合深夜独自开车的纯音乐，不要歌词。”

失败表现：强迫用户先写歌词、虚构歌手与人物关系，或生成空的Controlled Lyrics。

通过标准：作品标记为 `instrumental`，从用途、身体/情绪变化和主题动机进入声音方向；产物为Style Prompt与Instrumental Form，不执行歌词锁、主唱和逐字符检查。

### 场景 E：用户从音乐片段进入

用户提供一段旋律级数、节奏细胞、groove、riff、和声循环、主题动机、演唱动作或局部编曲，并说明哪些部分不可改。

失败表现：重新从完整声音方向开始并丢掉片段；强迫补完整歌曲；把文字描述冒充已经听见的音频。

通过标准：识别片段种类、表达、上下文作用、锁定维度、开放维度和目标。只炼片段时停在片段结果；发展完整包时把片段作为受保护资产回装。人声分支需要歌词时读取锁定歌词，器乐分支不得接受演唱动作。

## 4. `laohu_lyrics` 压力场景

### 场景 A：用户要求快速完整稿

失败表现：省略人物、诗性和整体冷读，直接顺写第一版；或启动多个完整候选。

通过标准：同一调用内部完成有限高价值搜索、全歌契约、完整初稿和冷读，只输出一份修后稿。

### 场景 B：逐乐段创作诱惑

用户说：“每个乐段单独写，速度更快，最后拼起来。”

失败表现：各段人物声口、物象和核心句不一致。

通过标准：允许逐段落笔和精修，但每次必须读取全歌契约与完整歌词；不得孤立生成后直接拼接。

### 场景 C：逐字打磨诱惑

用户要求：“每个字都给我三个替代。”

失败表现：制造大量虚假选择，句子和人物被局部最优破坏。

通过标准：每字检查，但只有承重字存在可定位缺陷时才提供候选；其他字标记 `keep`。

### 场景 D：用户新反馈只强调一个规则

失败表现：只执行新反馈，忘记自然中文、人物知识和此前锁定核心句。

通过标准：新反馈改变本轮侧重，全部锁定项和不可补偿边界继续生效。

### 场景 E：抓人的开场与全歌断开

初稿第一句很反常识，后文却只回到普通异地恋叙事，核心句和Final都没有回答第一句留下的问题。

失败表现：因第一句单独传播性强而保留，或只把后文情绪写得更重。

通过标准：开场认知缺口必须被人物证据、核心句和后文共同兑现；无法同轴时改开场或返回命题，不把标题党当歌曲结构。

### 场景 F：抽象副歌看似金句

副歌使用“爱、勇气、遗憾、命运”等公共词，单独摘出很顺，但放回全歌没有更窄含义。

失败表现：因为容易理解和转发就判为核心句成立。

通过标准：执行摘出/放回双向测试；前文必须把抽象词缩窄为当前人物的对象、代价和关系动作。

### 场景 G：越来越痛冒充格局扩大

Verse、Pre、Chorus和Bridge只让“想念、害怕、舍不得”逐段加强。

失败表现：增加人生、命运、世界等大词，或让人物简单决定离开就宣布升维。

通过标准：严肃作品至少检查对象、时间、因果、价值或行动中的一条尺度轴，并从私人事实长出、回到人物现实；轻甜作品按自身边界处理。

### 场景 H：Bridge用总结冒充理解变化

Bridge连续使用“原来、其实、终于懂了”总结前文，没有新事实或句法推进。

失败表现：换成更华丽的哲理句。

通过标准：使用一项可听见的事实或句法发动机逐步改变旧理解，并使Final核心句获得新含义；不需要Bridge时允许删除。

### 场景 I：文化材料扩大格局

歌词罗列神话、历史人物和名句证明爱情道理。

失败表现：因文化感和知识量判为诗性或格局成立。

通过标准：只保留结构同源、人物有权、完成当前语言转译、第一耳独立成立且真正推进作品的最少材料。

### 场景 J：字数整齐冒充可唱

副歌四行字数和韵脚一致，但全部同起拍、同密度、同休止和同尾音；Pre也用相同的两小节幻觉。

失败表现：因朗读顺口和字数整齐判为节奏成立，或为全歌填写伪精确音符矩阵。

通过标准：只给主Hook与风险句建立起拍、密度、跨度、休止、重音和尾音的时间假设，由声音阶段接受、修改或拒绝；普通句不增加默认矩阵。

### 场景 K：用名人头衔证明顶尖

高上限作品在样本出现前同时要求从多位顶尖作词人角度投票。

失败表现：模拟本人意见、平均冲突审美、复制标志性语言，或只写“参考某某”没有改变正文。

通过标准：样本出现后最多选择一个公开可核对的成熟机制，必须改变或淘汰一个具体决定，并记录反模仿边界；没有实际改变时视为未校准。

## 5. `laohu_sound` 压力场景

### 场景 0：纯音乐分支

失败表现：因为没有锁定歌词而拒绝，或把纯音乐当作删除人声的歌曲模板。

通过标准：从使用场景、注意、身体脉冲、张力/释放、唯一主题动机、形式、groove/和声、配器/音色、转场和结尾建立完整方向；输出Style Prompt与Instrumental Form，保留外部音频多轮反馈能力。

### 场景 0.5：音乐片段局部目标

用户只要求把副歌尾部两拍的旋律或节奏炼好，不要求完整提示词包。

失败表现：生成完整Style Prompt、改动锁定音高或歌词、宣称片段已是完整作品。

通过标准：`music_fragment`模式只处理开放维度，回测必要歌词/形式上下文后交付结构化片段并停止；只有用户目标是完整包时才进入声音方向与完整回装。

### 场景 A：没有音频

失败表现：返回等待音频，或声称已经听见旋律效果。

通过标准：完成声音方向选择和提示词包；把喜耳度、平台遵从和真人音区标为外部验证。

### 场景 B：用户要求排列组合

失败表现：把不同方向的旋律、groove、和声和音色任意拼接。

通过标准：只允许AI证明兼容的从属维度调整，保留一个最高记忆中心。

### 场景 C：外部音频不好

失败表现：增加更多标签或重写全包。

通过标准：先描述可观察差异和最早根因，只改最小必要字段；本轮后等待新音频。用户带来新音频时允许继续下一轮，不把“一轮一修改”误解成总共只能修一次。

### 场景 D：运行环境不能直接听音频

失败表现：假装听见演唱情绪，或拒绝用户的文字反馈。

通过标准：声明 `user_text_only`，以用户感受为主要证据；能使用工具时只补充实际可分析的技术指标，不冒充人类审美听感。

### 场景 E：用户连续返回多轮生成结果，但不报内部 ID

压力：第一轮用户只说“人声太远”，第二轮又说“人声近了，但副歌鼓太满”，第三轮同一提示词一次生成两个差异很大的版本。

失败表现：要求用户自己编写 `audio_run_id`；第二轮覆盖第一轮已成立的人声距离；把第三轮的平台随机差异误当成一条稳定提示词问题；一轮修订后自动宣布完成。

通过标准：系统自动登记并关联 ID；每轮保存父版本、来源证据、保留资产、同根因修改组和下轮可观察预期；同提示词多结果先判断稳定性；用户可继续任意多轮。

### 场景 F：用户暂停或接受

失败表现：用户说“先放着”就把版本标成已接受；或者用户明确说“这版可以”后仍自动追加修订。

通过标准：暂停只保存可恢复的当前状态；明确接受时执行 `accept_sound_package`，锁定确切 `prompt_revision_id` 并结束循环。

### 场景 E：只改BPM修律动

外部音频速度大致合适，但鼓、bass、人声切分和riff彼此不咬合，密集中文没有空间。

失败表现：只把90 BPM改成86或94 BPM。

通过标准：区分BPM与groove，诊断重拍、鼓贝、人声、riff、空拍和中文让位，并只修改最早导致身体感错误的一组字段。

### 场景 F：克制被生成成平淡

提示词要求克制、温暖和亲密，结果所有乐段都低音区、低动态、同一人声距离，Final决定听不出来。

失败表现：改成全程更强、更高、更响。

通过标准：分别检查旋律、节奏密度、编曲和人声表演四条曲线，恢复人物内部压力；只选择必要主变化，不把克制与爆发做成二选一。

### 场景 G：中文在旋律上难懂

高点落在闭口弱字，关系判词被切碎，数字和专名挤在快速乐句里。

失败表现：只要求“clear Mandarin diction”或擅自改歌词。

通过标准：在歌词锁定内调整重音、时值、句形、休止和编曲让位，区分母音展开、辅音收口和声调风险；把真实成立留给外部生成或试唱验证。

## 6. `laohu_learning` 压力场景

### 场景 A：一次强烈反馈

用户说：“以后永远不要写雨、灯、风。”

失败表现：建立永久禁词。

通过标准：记录表面反馈，追查是否来自库存检索、选择性知觉或替换损失；无跨作品证据时只作为当前要求或candidate，并保留常见意象被重新授权的反例。

### 场景 B：个人偏好冒充专业规则

用户在两个成立副歌中选择更克制的一版。

失败表现：把“副歌必须克制”写入通用知识。

通过标准：记录题材和候选对照的偏好证据，置信度低；新题材继续询问。

### 场景 C：理论正确但当前结果未认可

失败表现：AI因自己的解释合理就将经验晋级active。

通过标准：结果未被用户认可时不得晋级；先修当前作品，再等待验证与授权。

## 7. 部署通过条件

- 四个Skill都能从描述字段被正确触发。
- 每个Skill明确不适用场景和权限边界。
- 压力场景中的失败路径被Skill正文明确阻断。
- Skill不复制完整通用知识，只引用权威文件。
- 每个Skill保持一个岗位、多个明确模式，不重新生长成岗位群。
