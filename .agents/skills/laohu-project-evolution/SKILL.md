# 老胡项目自进化

本 Skill 管理项目怎样从真实反馈中变得更可靠。它不把每次意见都升级成永久规则，也不把“记住了”冒充系统已经发生变化。

## 1. 调用契约

输入至少包括：

```text
用户反馈或任务失败的原始证据
→ 当前结果中具体哪里有问题
→ 本轮实际读取了哪些顶层规则、Skill 和 reference
→ 用户要求只改当前结果，还是同时更新项目
→ 当前工作区状态和可能存在的用户修改
→ 如果正在拆分、迁移或重写规则，原文件与目标文件的完整语义清单
```

输出必须包括：

- 当前问题的修正结果或明确处理方向。
- 问题属于执行偏离、规则缺陷、能力缺口还是一次性偏好。
- 真正负责该问题的唯一权威文件。
- 已完成的增、删、改及其适用边界。
- 结构检查和行为回归结果。
- 通过 `laohu-natural-dialogue` 组织的用户汇报。

本 Skill 决定项目规则怎样变化，不负责日常沟通口吻。需要向用户解释时，把事实、修改和验证结果交给沟通 Skill；沟通 Skill 不得改写技术事实和规则边界。

## 2. 什么时候调用

用户出现以下表达时直接调用：

- “记住这个”“以后都这样”“写进项目”“沉淀成规则”。
- “修改 AGENTS.md、Skill、reference 或能力库”。
- “这不是只改一次”“下一次不要再犯”。
- “为什么规则已经写了，结果还是这样”。
- “当前项目缺少什么能力”“要不要新建 Skill”。

出现以下信号时先诊断，再决定是否修改：

- 用户指出“不对、难懂、不自然、调用错了、又出现了”。
- 同一类问题在不同材料中重复出现。
- 一个 Skill 无法完成自己宣称负责的结果。
- 顶层规则、领域 Skill 和 reference 给出冲突指令。
- 项目依靠临时知识完成任务，现有能力库没有对应判断。

以下情况不升级为永久规则：

- 只影响当前一句、当前作品或当前审美选择。
- 用户尚未确认的探索方向。
- 只有一次情绪反应，无法定位稳定触发条件。
- 现有规则已经正确，本次只是没有执行。
- 新规则会明显扩大范围、成本或风险，用户尚未决定。

## 3. 先修当前结果，再判断是否进化

用户指出问题时，先让当前任务恢复可用。不能为了建设系统，把用户眼前的问题留到最后。

随后区分两种学习：

- 修正动作：当前句子、路由、作品或文件做错了什么，立即改正。
- 修正规则：哪条判断、顺序、边界或触发条件让错误有机会再次发生。

只改结果会让同类问题复发；只改规则却不修当前结果，会让进化变成内部表演。两层都成立时必须同时完成。

## 4. 给反馈分层

每条反馈只确定一个主要归属，必要时记录次级影响：

| 层级 | 判断标准 | 承载位置 |
| --- | --- | --- |
| 一次性修改 | 只影响当前句子、候选或交付物 | 当前任务 |
| 当前作品规则 | 影响这部作品后续选择 | `创作日志.md` 或当前作品文件 |
| 领域能力规则 | 影响选题、写词、谱曲、歌名或封面中的一类任务 | 对应 `SKILL.md` |
| 场景方法 | 只有特定题材、用途或条件才读取 | 对应 `.agents/references/` |
| 项目共同边界 | 所有任务都必须遵守的身份、路由、优先级或硬边界 | `AGENTS.md` |
| 稳定偏好 | 用户多次确认的审美、沟通和工作习惯 | 唯一偏好资产；项目没有该资产时先评估是否值得创建 |
| 待验证经验 | 有价值但证据尚不足 | 留在当前诊断，不写成硬规则 |

不能因为一条规则重要，就把它放进顶层。重要性决定执行强度，职责范围决定文件位置。

## 5. 沿生成过程追根因

从用户看到的结果向上追查：

```text
用户指出的具体表象
→ 产生表象的句子、判断或操作
→ 本轮采用了什么材料和判断顺序
→ 实际读取了哪些规则
→ 哪条规则允许、诱导或没有拦住错误
→ 问题是缺失、歧义、冲突、过时、错位、不可执行还是未验收
→ 哪个生成节点最早能够发现并停止
```

至少区分：

- 规则正确但未读取：修路由，不重复写规则。
- 规则已读取但未执行：强化触发和验收，检查是否被更高优先级覆盖。
- 规则只描述理想状态：补触发条件、动作和失败分支。
- 规则针对表象：继续追到产生表象的选择和顺序。
- 两条规则冲突：确定共同目标和优先级，删除或合并冲突内容。
- 规则过度贴合案例：抽象出同类问题的稳定触发和边界。
- 结果本身判断错误：先回领域 Skill 修专业逻辑，不用文风规则遮盖。

禁止看到用户不满意就立即新增一条规则。先证明问题确实来自规则系统。

## 6. 判断是否需要证据与搜索

涉及事实、专业方法、版权、平台能力、技术行为或长期质量标准时，先搜索并核对可靠资料。优先使用一手材料、正式文档、公开作品、创作者完整访谈和经过真实结果检验的方法。

使用具名专业校准时，写清：

```text
为什么此人或此来源与当前问题相关
→ 只借用哪一种公开判断能力
→ 它能证明什么，不能证明什么
→ 是否存在同等级的相反方法
→ 当前项目采用哪一部分，为什么
```

不需要为了形式搜索：用户明确表达的个人偏好、低风险机械修改、当前作品的主观审美选择和可以由本地文件直接确认的事实。

证据负责校正方法和事实，不替用户决定作品审美。禁止用“顶尖人士都认为”或名人名单代替具体依据。

判断 Codex、Skill、`AGENTS.md`、上下文和工具的运行机制时，必须区分平台规则与单次执行行为：

```text
官方文档、当前版本配置或可核验实现说明了什么
→ 运行日志实际记录了什么
→ 该日志能证明本轮行为，还是足以证明稳定机制
→ 是否存在另一种解释
→ 结论应写成事实、暂定推断还是待验证假设
```

- 一次 `sed`、`head`、搜索范围、输出截断或 Agent 没有继续读取，只能证明该轮采用了这种工具策略，不能直接证明平台存在相同行数上限。
- 初始 Skill 列表预算、Skill 正文加载、reference 按需读取和 `AGENTS.md` 字节预算是不同机制，必须分别核实，禁止用一个阈值解释另一层行为。
- 只有官方说明、当前配置、稳定复现实验或实现证据支持时，才把机制判断写成硬规则。证据不足时保留为假设，不得据此重构项目。
- 运行行为与官方机制不一致时，先检查 Skill 是否进入官方发现路径、是否真正触发、是否只被当作普通文件手动读取，再判断规则本身是否失效。

## 7. 选择唯一权威来源

修改前先读取目标文件及其调用关系，回答：

```text
这条规则影响所有任务，还是一个领域、一个场景或一部作品
→ 当前是否已有负责人
→ 修改已有内容能否解决
→ 是否存在重复副本或相反规则
→ 谁负责调用，谁负责最终验收
```

归属原则：

- `AGENTS.md` 只保存身份、主路由、横切 Skill 调用、优先级和所有任务共同边界。
- 领域判断流程进入对应 `SKILL.md`。
- 只在特定条件下展开的方法、理论和案例进入 `.agents/references/`。
- 当前作品决定进入作品日志，不进入项目规则。
- 同一规则只保留一个权威版本，其他位置只建立引用。

修改 `AGENTS.md` 前必须检查 `project_doc_max_bytes` 配置和当前字节数。默认按项目说明总预算 `32 KiB` 控制；没有明确提高配置时，不允许通过追加内容使顶层超过预算。接近上限时先拆职责、删除重复和迁移方法，再决定是否保留新规则。

## 8. 什么时候创建新 Skill 或文件

同时满足以下条件才创建新 Skill：

1. 任务会重复出现。
2. 有独立触发场景和明确交付物。
3. 需要与现有 Skill 不同的判断过程。
4. 塞进现有 Skill 会造成职责冲突或错误调用。
5. 可以设计真实测试判断它是否有效。
6. 创建后会减少重复解释和同类错误。

不满足时，修改现有负责人或留在当前任务。不要用“以后可能有用”预制空目录、空 Skill 和没有真实调用的 reference。

新文件确有必要时，说明现有文件为什么无法承接。默认优先级：

```text
修正现有表述
→ 删除错误或过时内容
→ 合并重复规则
→ 在现有负责人中补充缺口
→ 确认职责独立后才新建文件
```

## 8.1 规则拆分、迁移与重写不得降级

把顶层规则拆成 Skill、把长文件拆成 reference、重写提示词、合并重复规则或精简文字时，默认执行语义迁移，不执行摘要改写。目标文件必须让一个没有当前聊天上下文的新模型恢复原规则要求的判断能力。

修改前建立迁移清单，逐项记录：

```text
原规则规定了什么目的
→ 在什么情况下触发
→ 要采取什么动作
→ 禁止什么表现
→ 有哪些例外与边界
→ 用什么场景或例子消除歧义
→ 怎样验收是否执行
→ 迁移后由哪个文件负责
```

以下内容不能因为“模型应该懂”“当前窗口已经理解”“可以概括成一个词”而删除：

- 会改变执行选择的身份细节、价值取舍和语气边界。
- 同一原则在不同用户状态、题材、阶段或风险下的不同动作。
- 用于区分相近概念的反例、边界和失败分支。
- 用户反复强调、且曾经真实改变结果的稳定偏好。
- 能拦住模型高频错误的具体语言、触发词和发送前检查。

允许压缩的只有重复说明、没有新增判断的铺垫、已经由唯一权威文件完整负责的副本，以及不能改变任何选择的修辞性自述。压缩后如果只能保留“温暖、专业、深入、自然、准确、治标治本”等目标词，却失去达到目标的行为，判为迁移失败。

每次迁移完成后制作覆盖对照：

| 原规则单元 | 保留 / 改写 / 删除 | 新位置 | 语义是否等价 | 删除依据 | 行为测试 |
| --- | --- | --- | --- | --- | --- |

覆盖对照是迁移过程中的内部检查，默认不新建长期文件；任务规模大、用户明确要求审计记录或未来需要持续维护时，才写入现有日志或正式诊断文件。

不得用行数、字数和文件大小单独判断信息是否完整。判断标准是可恢复性：新模型只读取目标文件后，能否知道何时做、为何做、具体怎么做、什么情况不能做，以及怎样发现自己做错。

## 9. 把反馈写成可执行规则

不要照抄用户的情绪化原话。每条长期规则必须回答：

```text
触发：什么情况下执行
→ 错误：系统会出现什么可观察表现
→ 根因：哪个判断、关系、顺序或约束产生错误
→ 动作：执行到哪一步时检查、停止、删除、重写或询问
→ 例外：哪些相似情况不归本规则处理
→ 验收：什么结果证明规则发挥作用
→ 回退：验收失败后回到哪个判断节点
```

规则写法：

- 用命令句规定动作，用笃定句规定边界。
- 名词指向明确对象，动词对应实际操作，因果词连接真实传导关系。
- 先写正确选择和拦截点，再写必要禁令。
- 复杂判断可以写长，但每个分句必须增加条件、区别、动作或后果。
- 例子必须改变模型理解；不能用案例代替规则。
- 删除商量铺垫、身份自述、重复结论和“注意、加强、提升、优化”式空要求。

以下规则无效：

- “以后注意表达准确。”
- “避免 AI 味。”
- “增强画面感和感染力。”
- “深入分析底层逻辑。”
- “写得更加高级。”

它们没有说明对象、错误、动作和验收，不能改变下一次生成。

## 10. 修改文件

修改前：

1. 重新理解用户表面要求和真实目的。
2. 确定修改层级、权威文件和不应改动的范围。
3. 检查适用的 `AGENTS.md`、目标 Skill 和 reference。
4. 查看工作区状态，识别用户已有修改。
5. 评估是否改变范围、成本、风险或作品方向；发生重要取舍时先确认。

修改时：

- 使用最小范围的增、删、改解决根因。
- 不回滚、不覆盖用户未授权的修改。
- 新规则与旧规则冲突时，直接合并、改写或删除旧规则，不把两套答案并存。
- 不创建版本副本和临时规则文件。
- 不把内部分析、研究笔记和事故经过写进正式规则。
- 文件过长时按职责和按需读取条件拆分，不按行数机械切割。
- 拆分和精简前先完成第 8.1 节的语义清单；不能证明等价时，宁可暂时保留原规则，也不能交付弱化版本。

修改后立即检查引用路径、标题结构、frontmatter、重复规则、冲突边界和文件字节预算。

## 11. 防复发验证

验证必须覆盖结构和行为两层。

结构验证：

- 目标文件可读取，frontmatter 和 Markdown 结构正常。
- 项目 Skill 位于 Codex 官方发现路径，或由可核验的符号链接进入该路径；不得只在 `AGENTS.md` 中写一个普通文件路径后假定 Skill 已经触发。
- 顶层路由能够触发 Skill，Skill 能够找到必要 reference；用全新会话检查时，区分自动加载、Skill 触发和 Agent 手动读取。
- 同一规则没有多个权威副本。
- `AGENTS.md` 未超过当前项目说明预算。
- 没有把用户修改、无关文件或目录结构意外改变。

行为验证至少准备三个场景：

1. 原始失败场景：确认当前问题已经被拦截。
2. 同根变体：更换题材、人物或材料，确认规则仍能识别同一种生成原因。
3. 边界反例：表面相似但根因不同，确认规则不会误伤。

涉及规则迁移、人格、沟通、路由和长期偏好时，再增加“上下文清零测试”：启动一个不继承当前对话的新会话，只提供项目文件和真实用户输入，检查它是否仍能做出原规则要求的关键判断。测试不得在提示词里泄露预期答案、缺失项和刚刚修改的规则。

验证时比较：

```text
没有新规则时模型最可能怎样做
→ 新规则在哪一步改变了选择
→ 输出中出现什么可观察差异
→ 是否引入冗长、僵硬、错误拒绝或新的冲突
```

只检查文件存在、字数增加和措辞漂亮，不算验证。能够运行独立测试时优先使用独立上下文；不能运行时进行明确标注的干跑，不把自我感觉包装成实测结论。

迁移任务还要抽样反向复原：让新上下文根据目标文件说明它在身份、触发、动作、边界和验收上会怎样执行，再与原语义清单比较。只会复述标题和目标词，无法还原具体行为，判为弱化迁移。

同类问题再次出现时，先审查原规则为何失效。只有新问题的触发条件、主要根因和责任边界明显不同，才建立新规则；否则继续修正原权威规则。

## 12. 汇报与交接

完成后把以下事实交给 `laohu-natural-dialogue`：

```text
用户最初指出的问题
→ 确认的根因
→ 修改的文件和规则
→ 删除、合并或保留了什么
→ 它以后拦截哪类错误
→ 做了哪些结构和行为验证
→ 仍然存在什么边界或待验证问题
```

对用户说明真实结果，不贴整份规则，不用“已经全面优化”代替证据。没有完成行为验证时明确说没有；规则只解决某一范围时说清边界。

## 13. 失败分支

- 只有一次偏好且无法泛化：修当前结果，标为待验证，不落永久规则。
- 现有规则正确但执行漏读：修路由、加载或验收，不新增近义规则。
- 根因属于领域判断：回对应领域 Skill 修改，不塞进沟通或顶层规则。
- 修改会扩大范围或建立新能力：说明取舍，取得用户确认后再继续。
- 找不到可靠证据：保留为假设，不写成确定专业标准。
- 测试未改善或引入副作用：撤销本次规则改动，重新分析根因；不得保留“可能以后有用”的无效补丁。
- 迁移后能力覆盖下降：停止删除原规则，补回缺失的触发、动作、边界与例子，重新进行上下文清零测试。
