# 老胡项目自进化

本 Skill 管理项目怎样从真实反馈中变得更可靠。它不把每次意见都升级成永久规则，也不把“记住了”冒充系统已经发生变化。

## 1. 调用契约

输入至少包括：

```text
用户反馈或任务失败的原始证据
→ 当前结果中具体哪里有问题
→ 本轮实际读取了哪些顶层规则、Skill 和 reference
→ 用户要求只改当前结果，还是同时更新项目
→ 当前工作区状态和可能存在的用户修改
→ 如果正在拆分、迁移或重写规则，原文件与目标文件的完整语义清单
```

输出必须包括：

- 当前问题的修正结果或明确处理方向。
- 问题属于执行偏离、规则缺陷、能力缺口还是一次性偏好。
- 真正负责该问题的唯一权威文件。
- 已完成的增、删、改及其适用边界，或本轮不应修改永久规则的证据。
- 结构检查和行为回归结果。
- 通过 `laohu-natural-dialogue` 组织的用户汇报。

本 Skill 决定项目规则怎样变化，不负责日常沟通口吻。需要向用户解释时，把事实、修改和验证结果交给沟通 Skill；沟通 Skill 不得改写技术事实和规则边界。

## 2. 什么时候调用

用户出现以下表达时直接调用：

- “记住这个”“以后都这样”“写进项目”“沉淀成规则”。
- “修改 AGENTS.md、Skill、reference 或能力库”。
- “这不是只改一次”“下一次不要再犯”。
- “为什么规则已经写了，结果还是这样”。
- “当前项目缺少什么能力”“要不要新建 Skill”。

出现以下信号时先诊断，再决定是否修改：

- 用户指出“不对、难懂、不自然、调用错了、又出现了”。
- 同一类问题在不同材料中重复出现。
- 一个 Skill 无法完成自己宣称负责的结果。
- 顶层规则、领域 Skill 和 reference 给出冲突指令。
- 项目依靠临时知识完成任务，现有能力库没有对应判断。

以下情况不升级为永久规则：

- 只影响当前一句、当前作品或当前审美选择。
- 用户尚未确认的探索方向。
- 只有一次情绪反应，无法定位稳定触发条件。
- 现有规则已经正确，本次只是没有执行。
- 新规则会明显扩大范围、成本或风险，用户尚未决定。

## 3. 先修当前结果，再判断是否进化

用户指出问题时，先让当前任务恢复可用。不能为了建设系统，把用户眼前的问题留到最后。

随后区分两种学习：

- 修正动作：当前句子、路由、作品或文件做错了什么，立即改正。
- 修正规则：哪条判断、顺序、边界或触发条件让错误有机会再次发生。

只改结果会让同类问题复发；只改规则却不修当前结果，会让进化变成内部表演。两层都成立时必须同时完成。

诊断不是完成状态。用户明确要求自我进化，或本轮已经确认存在可复用的执行、规则或验收缺口时，按下面的状态推进：

```text
DIAGNOSED：已经说清表象、根因和最早断点
→ CURRENT_FIXED：当前错误结果或错误状态已经撤回、修正或明确阻断
→ SYSTEM_DECIDED：完成准入卡，得到 NO_CHANGE / REPLACE / MERGE / ADD / MOVE_TO_CURRENT_WORK
→ SYSTEM_APPLIED：除 NO_CHANGE 外，权威文件已经发生实际修改
→ VERIFIED：结构检查和原始失败、同根变体、边界反例已经回放
```

停在`DIAGNOSED`、只说“应该增加什么规则”或“下一次会注意”，不得对外宣告已经优化。允许结束的只有两种情况：一是当前结果已修正，并用现有规则的具体触发、动作和回退证明`NO_CHANGE`；二是当前结果与权威规则均已实际修改，并完成相称的回归验证。若因授权、事实或工具限制不能落地，必须明确报告尚停在哪个状态和缺少什么，不能用建议稿冒充项目变化。

## 4. 给反馈分层

每条反馈只确定一个主要归属，必要时记录次级影响：

| 层级 | 判断标准 | 承载位置 |
| --- | --- | --- |
| 一次性修改 | 只影响当前句子、候选或交付物 | 当前任务 |
| 当前作品规则 | 影响这部作品后续选择 | `创作日志.md`、`歌词创作台.md` 或当前作品文件 |
| 领域能力规则 | 影响选题、写词、谱曲、歌名或封面中的一类任务 | 对应 `SKILL.md` |
| 场景方法 | 只有特定题材、用途或条件才读取 | 对应 `.agents/references/` |
| 项目共同边界 | 所有任务都必须遵守的身份、路由、优先级或硬边界 | `AGENTS.md` |
| 稳定偏好 | 用户多次确认的审美、沟通和工作习惯 | 唯一偏好资产；项目没有该资产时先评估是否值得创建 |
| 待验证经验 | 有价值但证据尚不足 | 留在当前诊断，不写成硬规则 |

不能因为一条规则重要，就把它放进顶层。重要性决定执行强度，职责范围决定文件位置。

## 5. 沿生成过程追根因

从用户看到的结果向上追查：

```text
用户指出的具体表象
→ 产生表象的句子、判断或操作
→ 本轮采用了什么材料和判断顺序
→ 实际读取了哪些规则
→ 哪条规则允许、诱导或没有拦住错误
→ 项目中还有哪些词面不同、却由同一种错误选择产生的旧失败与旧规则
→ 问题是缺失、歧义、冲突、过时、错位、不可执行还是未验收
→ 哪项上游判断能力缺失，才会持续生成这一簇不同表象
→ 哪个生成节点最早能够执行这项判断并停止
```

至少区分：

- 规则正确但未读取：修路由，不重复写规则。
- 规则已读取但未执行：强化触发和验收，检查是否被更高优先级覆盖。
- 规则只描述理想状态：补触发条件、动作和失败分支。
- 规则针对表象：继续追到产生表象的选择和顺序；把专名换成类别名不等于已经找到根因。
- 两条规则冲突：确定共同目标和优先级，删除或合并冲突内容。
- 规则过度贴合案例：抽象出同类问题的稳定触发和边界。
- 结果本身判断错误：先回领域 Skill 修专业逻辑，不用文风规则遮盖。

禁止看到用户不满意就立即新增一条规则。先证明问题确实来自规则系统。

### 5.1 根因不是放大后的表象

根因必须是一项会在多种材料、题材或任务中反复影响选择的能力缺口，例如：输入事实没有同步、候选没有先比较、语义角色没有核对、段落责任没有预先确定。表象只描述这一次错写；把表象换成更大的类别名仍只是局部规则；根规则必须说明正确生成依赖什么共同输入、怎样比较与裁决，并能同时处理多个外观不同的失败。

每次准备把反馈写入长期规则前，先建立失败簇：

```text
当前表象：用户这次看见了什么
同根旧例：项目规则、历史失败或现有验收中，至少两种词面不同的表现
共同错误选择：系统在这些例子里都依据了什么错误信息，漏掉了什么比较，或把哪一步放晚了
所需正向能力：正确生成时应先建立什么输入、比较什么候选、按什么证据裁决
执行位置：这项能力第一次能够改变选择的节点
冗余清单：根规则成立后，哪些旧禁令、词表、检查项或当前作品事实应删除、合并或下沉
```

没有找到同根旧例，不自动证明不应进化；但只能在可靠理论、稳定复现或明显的基础能力缺失能够证明其通用性时写入长期规则。否则保留为当前作品规则或待验证经验。禁止仅把人名、物件、题材和原句换成上位词，就宣称已经从案例提炼完成。

长期规则按根、枝、叶分层：

- **根规则**写正向选择能力、输入、顺序、裁决和回退，进入每次都必须读取的主 Skill。
- **条件方法**说明某类乐段、题材、平台或风险怎样实现根规则，进入对应 Skill 分支或按需 reference。
- **案例证据**保存具体错句、词表、事故和边界反例，只用于专项解释与回归；失败原句进入测试或既有复盘，当前候选留在所属作品，不进入通用生成 reference。

修复与合并类根规则应解释不同表现下的共同错误选择，确有被覆盖的补丁时清理它们。首次新增能力以明确能力缺口、可靠依据、可执行方法与正反场景证明准入；没有旧例或旧补丁时如实记录，不虚构案例或删除无关能力凑数。缺少这些证据时先作为待验证方法，不因措辞抽象就升级。

### 5.2 规则变更准入门

修改 `AGENTS.md`、Skill 或 reference 之前，必须先在本轮内部完成下面这张准入卡；不得边写规则边补理由：

```text
现有覆盖：哪个权威文件已经规定了什么，本轮是否真正执行
失败类型：未读取 / 已读未执行 / 规则歧义 / 规则缺失 / 规则冲突 / 单次偏好
失败簇：除当前表象外，项目内哪些不同表象由同一错误选择产生
能力根因：缺失或错误的是哪项输入建模、候选比较、证据裁决、状态同步或回退能力
最早断点：这项正向能力第一次能改变选择的生成、路由、交接或验收位置
作用尺度：整部作品 / 某类乐段或模块 / 当前作品 / 当前候选；上层目标落到不同局部时是否需要不同实现
可迁移判断：去掉作品名、题材、人名、原句和当前物件后，还剩下哪个会改变选择的条件与动作
架构位置：根规则 / 条件方法 / 案例证据 / 当前作品事实
冗余处理：新规则生效后，哪些旧规则删除、合并、下沉或保留，理由是什么
变更结论：NO_CHANGE / REPLACE / MERGE / CONSOLIDATE / ADD / MOVE_TO_CURRENT_WORK
```

准入裁决：

- 现有规则已经同时写清触发、动作和失败回退，且若真正执行就会拦下当前错误，结论必须是 `NO_CHANGE`。修路由、执行产物或交付门，不向领域规则追加同义禁令。
- 现有规则只写了期望结果，没有说在哪一步做什么、失败回哪里，才能判为规则缺口。优先 `REPLACE` 或 `MERGE` 旧表述，不在文件末尾叠加一条“更明确”的重复规则。
- 可迁移判断仍包含当前作品的专名、原句、题材装饰或某一组韵脚，判为案例还没有提炼完成；选择 `MOVE_TO_CURRENT_WORK` 或待验证经验，不进入通用 Skill。
- 去掉具体词句后只剩“更自然、更有情绪、避免套路”等目标词，同样不算提炼。通用规则必须能指出：面对哪两个都说得过去的选择，根据什么条件改选，在哪一步停止错误。
- 去掉具体词句后只得到一个更大的类别名，例如把某个伤势错误改写成“不可逆事件检查”、把某个错搭改写成“高危动词检查”，仍未必是根因。继续寻找这些例子共同缺失的输入模型、比较动作或裁决顺序。
- 两条以上旧规则在拦截同一种错误选择时，优先 `CONSOLIDATE`：把正向能力提到最早责任点，把条件差异保留为分支，把具体失败词句移出生成资料，并删除主流程中的重复禁令。
- 从一个局部失败提炼出的规则若要求所有乐段、模块、题材或体式采用同一种实现，先判为尺度越权。保留上层共同目标，再分别说明不同局部怎样证明自己完成；不能把副歌的直接开口、主歌的画面入口、桥段的改判或尾声的余波互相复制。只有确实对所有局部成立的部分才进入全局规则，其余进入对应领域或场景负责人。
- 只有能完整说出“没有新规则时会继续做出什么错误选择，新规则会在哪一步改变这个选择”，并证明现有根规则无法通过 `REPLACE / MERGE / CONSOLIDATE` 承接，才允许 `ADD`。新增时处理实际被取代的旧补丁；若没有，记录“不适用”并证明新能力的独立作用与回归边界，不以增减数量作准入。

准入通过后，默认只修改最早责任点的唯一权威文件；当前作品可同时修正，回归案例可同时更新。若路由、领域规则和验收文件都需改动，必须分别说明它们各自修正的不同责任；说不出差异时，只保留最早责任点。

## 6. 判断是否需要证据与搜索

涉及事实、专业方法、版权、平台能力、技术行为或长期质量标准时，先搜索并核对可靠资料。优先使用一手材料、正式文档、公开作品、创作者完整访谈和经过真实结果检验的方法。

使用具名专业校准时，写清：

```text
为什么此人或此来源与当前问题相关
→ 只借用哪一种公开判断能力
→ 它能证明什么，不能证明什么
→ 是否存在同等级的相反方法
→ 当前项目采用哪一部分，为什么
```

不需要为了形式搜索：用户明确表达的个人偏好、低风险机械修改、当前作品的主观审美选择和可以由本地文件直接确认的事实。

证据负责校正方法和事实，不替用户决定作品审美。禁止用“顶尖人士都认为”或名人名单代替具体依据。

判断 Codex、Skill、`AGENTS.md`、上下文和工具的运行机制时，必须区分平台规则与单次执行行为：

```text
官方文档、当前版本配置或可核验实现说明了什么
→ 运行日志实际记录了什么
→ 该日志能证明本轮行为，还是足以证明稳定机制
→ 是否存在另一种解释
→ 结论应写成事实、暂定推断还是待验证假设
```

- 一次 `sed`、`head`、搜索范围、输出截断或 Agent 没有继续读取，只能证明该轮采用了这种工具策略，不能直接证明平台存在相同行数上限。
- 初始 Skill 列表预算、Skill 正文加载、reference 按需读取和 `AGENTS.md` 字节预算是不同机制，必须分别核实，禁止用一个阈值解释另一层行为。
- 只有官方说明、当前配置、稳定复现实验或实现证据支持时，才把机制判断写成硬规则。证据不足时保留为假设，不得据此重构项目。
- 运行行为与官方机制不一致时，先检查 Skill 是否进入官方发现路径、是否真正触发、是否只被当作普通文件手动读取，再判断规则本身是否失效。

### 案例进入通用资料的证据门

新增、维护或调用案例时，先区分公开原作、用户输入、项目自写候选、已完成作品与失败记录，核对来源、实际验证、用途和当前适用范围。来源不明、仅经模型自评、未确认或已被否决的项目文字，不作为通用创作示范、质量标杆或跨作品输入；仅标注“待验证”不能取得准入资格。先前采用过、文件保存很久或用户曾提供，都不证明质量成立。

通用生成资料保留可核验的外部作品机制及独立成立的方法；旧作品细节、候选胜负和失败原句从生成资料剥离。确有复现价值的失败仅留在测试或既有复盘记录，只有专项诊断时读取，不复制进常用 reference。格式占位与最小逻辑例子可以保留，但不得冒充成品或审美证据。当前用户明确指定旧作品续写、对标或复盘时，可读取该作品相关材料，效力限于本次任务，不自动升为跨作品范本。

## 7. 选择唯一权威来源

修改前先读取目标文件及其调用关系，回答：

```text
这条规则影响所有任务，还是一个领域、一个场景或一部作品
→ 当前是否已有负责人
→ 修改已有内容能否解决
→ 是否存在重复副本或相反规则
→ 谁负责调用，谁负责最终验收
```

归属原则：

- `AGENTS.md` 只保存身份、主路由、横切 Skill 调用、优先级和所有任务共同边界。
- 领域判断流程进入对应 `SKILL.md`。
- 只在特定条件下展开的方法、理论和案例进入 `.agents/references/`。
- 当前作品决定进入作品日志或歌词创作台，不进入项目规则。
- 同一规则只保留一个权威版本，其他位置只建立引用。

主 Skill 与 reference 的归属还要检查调用优先级：凡是每次生成都必须执行、会直接改变候选方向、决定停止或回流、或者负责把上层公理翻译到各类常见局部的规则，必须以可执行的紧凑形态留在主 Skill；不得把唯一实现降到按需 reference，再假定执行者一定会读取。Reference 负责理论来源、扩展类型、低频场景、标签歧义、详细案例和反向证据。一个上层能力向多个局部延伸时，主 Skill 应在该上层能力内部列出局部偏转，使执行顺序仍从上到下；只有不会改变常规选择的展开说明才下沉 reference。主文件过长时先删除重复、压缩例子和迁移证据，不以降低核心规则优先级换取篇幅整齐。

修改 `AGENTS.md` 前必须检查 `project_doc_max_bytes` 配置和当前字节数。默认按项目说明总预算 `32 KiB` 控制；没有明确提高配置时，不允许通过追加内容使顶层超过预算。接近上限时先拆职责、删除重复和迁移方法，再决定是否保留新规则。

## 8. 什么时候创建新 Skill 或文件

同时满足以下条件才创建新 Skill：

1. 任务会重复出现。
2. 有独立触发场景和明确交付物。
3. 需要与现有 Skill 不同的判断过程。
4. 塞进现有 Skill 会造成职责冲突或错误调用。
5. 可以设计真实测试判断它是否有效。
6. 创建后会减少重复解释和同类错误。

不满足时，修改现有负责人或留在当前任务。不要用“以后可能有用”预制空目录、空 Skill 和没有真实调用的 reference。

新文件确有必要时，说明现有文件为什么无法承接。默认优先级：

```text
修正现有表述
→ 删除错误或过时内容
→ 合并重复规则
→ 在现有负责人中补充缺口
→ 确认职责独立后才新建文件
```

## 8.1 规则拆分、迁移与重写不得降级

把顶层规则拆成 Skill、把长文件拆成 reference、重写提示词、合并重复规则或精简文字时，默认执行语义迁移，不执行摘要改写。目标文件必须让一个没有当前聊天上下文的新模型恢复原规则要求的判断能力。

修改前建立迁移清单，逐项记录：

```text
原规则规定了什么目的
→ 在什么情况下触发
→ 要采取什么动作
→ 禁止什么表现
→ 有哪些例外与边界
→ 用什么场景或例子消除歧义
→ 怎样验收是否执行
→ 迁移后由哪个文件负责
```

以下内容不能因为“模型应该懂”“当前窗口已经理解”“可以概括成一个词”而删除：

- 会改变执行选择的身份细节、价值取舍和语气边界。
- 同一原则在不同用户状态、题材、阶段或风险下的不同动作。
- 用于区分相近概念的反例、边界和失败分支。
- 用户反复强调、且曾经真实改变结果的稳定偏好。
- 能拦住模型高频错误的具体语言、触发词和发送前检查。

允许压缩的只有重复说明、没有新增判断的铺垫、已经由唯一权威文件完整负责的副本，以及不能改变任何选择的修辞性自述。压缩后如果只能保留“温暖、专业、深入、自然、准确、治标治本”等目标词，却失去达到目标的行为，判为迁移失败。

每次迁移完成后制作覆盖对照：

| 原规则单元 | 保留 / 改写 / 删除 | 新位置 | 语义是否等价 | 删除依据 | 行为测试 |
| --- | --- | --- | --- | --- | --- |

覆盖对照是迁移过程中的内部检查，默认不新建长期文件；任务规模大、用户明确要求审计记录或未来需要持续维护时，才写入现有日志或正式诊断文件。

不得用行数、字数和文件大小单独判断信息是否完整。判断标准是可恢复性：新模型只读取目标文件后，能否知道何时做、为何做、具体怎么做、什么情况不能做，以及怎样发现自己做错。

## 8.2 成熟 Skill 先认长处，再谈缺口

用户要求优化、重构、补能力或按四层深化一个成熟 Skill 时，必须读取[单一技能四层深化与保真迁移](../../references/laohu-project-evolution/单一技能四层深化与保真迁移.md)。先建立下面这条审计链，再决定修改：

```text
这个 Skill 独自负责哪一次专业转译
→ 哪些真实任务已经证明了它的长处
→ 哪些旧场景必须保护
→ 当前失败最早发生在哪一层
→ 缺口属于本 Skill、跨 Skill 交接、相邻负责人还是项目顶层
→ 本轮准备加厚什么，明确不补什么
```

成熟能力的优化先把长处拔高，再修阻碍长处发挥的断点；不以消灭所有短板为目标。若完整人物设计属于视觉资产能力，不能因为封面需要人物便把封面 Skill 改成角色设计系统；若歌名需要声音记忆，正确动作是修谱曲到歌名的交接，不是让歌名 Skill 学会作曲。

四层首先作用于目标 Skill 本身，但最终必须翻译成该领域的判断、关系、材料和法度。新规则可以显性解释四层，正式能力不能只复制“灵魂、筋骨、血肉、表皮”四个标题；它要让没有当前聊天上下文的模型知道这个领域具体要保护什么、怎样运行、使用什么材料、怎样交付和退回。

## 9. 把反馈写成可执行规则

### 规则箴言

```text
公理定方向，细则供解码，验收拦偏航。
先写要成什么，再写何时停。
禁令只拦已知错误，不能替代作品判断。
一条规则只护一个责任点，所有例外回到条件。
规则要让新作品会选，不只是让模型会复述。
```

当一次反馈暴露的是整个创作系统的平均化倾向，先检查是否把公理、机制、执行和验收平铺成同等权重。正确迁移不是再添一条“注意”，而是把旧内容归回四层：灵魂说明要保护的结果，筋骨说明选择怎样运动，血肉说明什么材料能承住它，表皮说明怎样落成；必要禁令只放在对应的验收门。若一条细则会阻止公理允许的有效变体，改成条件规则，不写成绝对禁令。

### “治标又治本”的判定

项目反馈只有同时修正当前结果和最早可阻断节点，才算完成“治标又治本”：

```text
治标：修掉当前输出中已经可见的错误，并把本案事实留在当前作品
→ 聚类：找出词面不同但由同一种错误选择造成的旧失败与旧补丁
→ 治本：建立能在生成前指导选择的正向能力，找到它第一次可以执行、停止或回流的节点
→ 归位：根规则进入主 Skill，条件方法进入分支或 reference，具体错句进入案例或当前作品
→ 清债：删除、合并或下沉已经被根规则覆盖的旧补丁
→ 回归：用原始失败、跨表象同根变体、边界反例和旧强项验证下一次选择确实改变
```

只增加“要更深、更自然、更有画面感”的目标词、只把具体名词换成类别名、只在交付后补一段检查，均判为治标；只改规则、不修当前作品，均判为项目内部表演。规则必须能让一个没有当前对话的新作品在生成前执行同样的判断，不能依赖用户再次指出例句。

不要照抄用户的情绪化原话。每条长期规则必须回答：

```text
触发：什么情况下执行
→ 错误：系统会出现什么可观察表现
→ 根因：哪个判断、关系、顺序或约束产生错误
→ 动作：执行到哪一步时检查、停止、删除、重写或询问
→ 例外：哪些相似情况不归本规则处理
→ 验收：什么结果证明规则发挥作用
→ 回退：验收失败后回到哪个判断节点
```

规则写法：

- 用命令句规定动作，用笃定句规定边界。
- 名词指向明确对象，动词对应实际操作，因果词连接真实传导关系。
- 先写正确选择和拦截点，再写必要禁令。
- 复杂判断可以写长，但每个分句必须增加条件、区别、动作或后果。
- 例子必须改变模型理解；不能用案例代替规则。
- 删除商量铺垫、身份自述、重复结论和“注意、加强、提升、优化”式空要求。

以下规则无效：

- “以后注意表达准确。”
- “避免 AI 味。”
- “增强画面感和感染力。”
- “深入分析底层逻辑。”
- “写得更加高级。”

它们没有说明对象、错误、动作和验收，不能改变下一次生成。

## 10. 修改文件

修改前：

1. 重新理解用户表面要求和真实目的。
2. 确定修改层级、权威文件和不应改动的范围。
3. 检查适用的 `AGENTS.md`、目标 Skill 和 reference。
4. 查看工作区状态，识别用户已有修改。
5. 评估是否改变范围、成本、风险或作品方向；发生重要取舍时先确认。

修改时：

- 使用最小范围的增、删、改解决根因。
- 不回滚、不覆盖用户未授权的修改。
- 新规则与旧规则冲突时，直接合并、改写或删除旧规则，不把两套答案并存。
- 新规则若声称解决根因，必须同步执行失败簇中的补丁清理；只新增根规则、仍把同义词表和单案禁令留在主流程，视为未完成。
- 不创建版本副本和临时规则文件。
- 不把内部分析、研究笔记和事故经过写进正式规则。
- 文件过长时按职责和按需读取条件拆分，不按行数机械切割。
- 拆分和精简前先完成第 8.1 节的语义清单；不能证明等价时，宁可暂时保留原规则，也不能交付弱化版本。

修改后立即检查引用路径、标题结构、frontmatter、重复规则、冲突边界和文件字节预算。

完成修改后必须查看实际差异，逐项把差异对应回准入卡中的最早断点。只有分析文字没有文件差异，状态仍是`DIAGNOSED`；只有规则差异没有当前结果修正，状态仍未达到`CURRENT_FIXED`；只有文件差异没有行为回放，状态不得标为`VERIFIED`。

## 11. 防复发验证

验证必须覆盖结构和行为两层。

结构验证：

- 目标文件可读取，frontmatter 和 Markdown 结构正常。
- 项目 Skill 位于 Codex 官方发现路径，或由可核验的符号链接进入该路径；不得只在 `AGENTS.md` 中写一个普通文件路径后假定 Skill 已经触发。
- 顶层路由能够触发 Skill，Skill 能够找到必要 reference；用全新会话检查时，区分自动加载、Skill 触发和 Agent 手动读取。
- 同一规则没有多个权威副本。
- `AGENTS.md` 未超过当前项目说明预算。
- 没有把用户修改、无关文件或目录结构意外改变。

行为验证至少准备三个场景：

1. 原始失败场景：确认当前问题已经被拦截。
2. 同根变体：更换题材、人物或材料，确认规则仍能识别同一种生成原因。
3. 边界反例：表面相似但根因不同，确认规则不会误伤。

根因型修改再增加两项：

4. 跨表象变体：不只更换题材和名词，还要更换错误的外观，确认同一正向能力仍会在上游改变选择。
5. 补丁冗余测试：逐条说明哪些旧禁令、词表或检查已经可由根规则推出；能够推出的必须删除、合并或降为案例。确有被覆盖的旧补丁却未处理，判为尚未治本；首次新增且没有旧补丁时，此项不适用，改验缺口是否由真实应用补齐。

优化成熟 Skill、迁移长规则或改变既有职责时，再增加“旧强项场景”：选择一项修改前已经做得好的代表任务，确认新规则没有为了补短板而削弱原本的判断速度、专业深度、审美锋芒、领域边界或交付质量。当前失败变少而旧强项退化，不能判为 `KEEP`。

涉及规则迁移、人格、沟通、路由和长期偏好时，再增加“上下文清零测试”：启动一个不继承当前对话的新会话，只提供项目文件和真实用户输入，检查它是否仍能做出原规则要求的关键判断。测试不得在提示词里泄露预期答案、缺失项和刚刚修改的规则。

验证时比较：

```text
没有新规则时模型最可能怎样做
→ 新规则在哪一步改变了选择
→ 输出中出现什么可观察差异
→ 是否引入冗长、僵硬、错误拒绝或新的冲突
```

只检查文件存在、字数增加和措辞漂亮，不算验证。能够运行独立测试时优先使用独立上下文；不能运行时进行明确标注的干跑，不把自我感觉包装成实测结论。

迁移任务还要抽样反向复原：让新上下文根据目标文件说明它在身份、触发、动作、边界和验收上会怎样执行，再与原语义清单比较。只会复述标题和目标词，无法还原具体行为，判为弱化迁移。

同类问题再次出现时，先审查原规则为何失效。只有新问题的触发条件、主要根因和责任边界明显不同，才建立新规则；否则继续修正原权威规则。

## 12. 汇报与交接

完成后把以下事实交给 `laohu-natural-dialogue`：

```text
用户最初指出的问题
→ 确认的根因
→ 修改的文件和规则
→ 删除、合并或保留了什么
→ 它以后拦截哪类错误
→ 做了哪些结构和行为验证
→ 仍然存在什么边界或待验证问题
```

对用户说明真实结果，不贴整份规则，不用“已经全面优化”代替证据。没有完成行为验证时明确说没有；规则只解决某一范围时说清边界。

## 13. 失败分支

- 只有一次偏好且无法泛化：修当前结果，标为待验证，不落永久规则。
- 现有规则正确但执行漏读：修路由、加载或验收，不新增近义规则。
- 根因属于领域判断：回对应领域 Skill 修改，不塞进沟通或顶层规则。
- 修改会扩大范围或建立新能力：说明取舍，取得用户确认后再继续。
- 找不到可靠证据：保留为假设，不写成确定专业标准。
- 测试未改善或引入副作用：撤销本次规则改动，重新分析根因；不得保留“可能以后有用”的无效补丁。
- 迁移后能力覆盖下降：停止删除原规则，补回缺失的触发、动作、边界与例子，重新进行上下文清零测试。
