# 老胡音乐学习与自进化

## 核心职责

先修正当前问题，再判断反馈是否值得成为个人偏好证据、根因经验、通用知识候选或项目运行规则。本Skill防止两种失败：只改表面导致重复犯错；把一次强烈反馈写成永久禁令导致规则膨胀。

## 必须读取

```text
AGENTS.md 的反馈与晋级规则
当前作品 state.yaml、work.md 和相关events
修改前后真实正文或外部结果
memory/profile.yaml
memory/records.jsonl 中同根因记录
schemas/memory-record.schema.json
```

没有当前证据时不凭用户一句概括制造根因。

## 模式

```text
feedback_diagnosis
record_candidate
validate_learning
promote_or_deprecate
compile_profile
```

一次调用只激活一个模式。

## 模式一：`feedback_diagnosis`

### 第一步：还原反馈

区分：

- 用户明确指出的作品表现。
- 用户对原因的推测。
- AI根据正文作出的推论。
- 尚无证据的可能性。

不得为了形成漂亮规则压缩掉用户真正反对的关系。

### 第二步：分类

```text
当前作品修改
一次性要求
客观专业缺陷
个人审美偏好
待验证根因
通用知识候选
项目运行规则
```

一条反馈可以同时影响当前作品和长期学习，但必须分别处理。

### 第三步：先修当前作品

反馈若指向当前结果，先把问题送回拥有修改权的歌词、声音或导演模式。当前结果未被用户认可前，不能因理论解释正确就晋级长期经验。

## 根因追踪

从表面表现向上追问：

```text
作品里具体出现了什么
→ 为什么伤害人物、情绪、语言、音乐或体验
→ 最早在哪个决策层发生
→ 模型为什么容易选择这条路径
→ 对应的人类认知、文学或音乐原理
→ 下次应改变哪个判断顺序
→ 作品里怎样证明已经改变
```

根因层只允许：命题、知识边界、观察位置、语言发动机、曲式、乐段、句子、字词、声音、平台和项目流程。

若修改一个词不能阻止同类问题复发，根因不在该词。若改变上游决定会无必要地重写大量成立内容，继续寻找更近的根因。

## “本”和“标”共同记录

每条根因经验必须包含：

| 内容 | 作用 |
|---|---|
| `surface_symptom` | 模型运行时能识别的表面表现 |
| `user_feedback` | 用户实际不接受什么 |
| `root_layer` | 最早错误决策层 |
| `causal_chain` | 表面怎样由上游机制产生 |
| `upstream_principle` | 人为什么会这样理解、感受或记忆 |
| `corrective_decision` | 下次具体改变哪个选择 |
| `positive_evidence` | 正确结果中出现什么 |
| `negative_evidence` | 失败结果中出现什么 |
| `boundary` | 哪些情况不适用 |
| `counterexample` | 表面相似但不应触发的情况 |
| `validation` | 当前和后续验证结果 |

只写底层理论会让模型不知道何时触发；只写表面禁令会过拟合当前事故。两者缺一不可。

## 偏好证据

个人偏好只在两个以上专业成立方案之间记录。包含：

- 题材、人物、关系阶段、乐段和决策维度。
- 用户看到的具体选项。
- 选择和拒绝。
- 用户明确理由；没有理由时区分AI推测。
- 与既有偏好的支持或冲突。
- 置信度和重新询问条件。

一次选择默认低置信。跨不同作品、相似决策重复成立才提高；新题材、高影响决定和冲突证据要求重新询问。

个人偏好不能进入 `knowledge/`，除非有独立专业证据证明它跨用户成立，并获得明确授权。

## 模式二：`record_candidate`

把诊断结果追加到 `memory/records.jsonl`：

- 一次观察用 `observed`。
- 已形成可验证根因用 `candidate`。
- 用户选择用 `preference_evidence`，状态不高于实际证据。
- 外部音频、听众或发布结果用 `external_result_evidence`。

记录必须通过Schema。不得改写旧证据来让新结论显得一致；冲突使用记录ID连接。

## 模式三：`validate_learning`

验证来源可以是：

- 当前作品修改前后对照且用户明确认可。
- 后续作品同根因对照。
- 真实外部音频、真人试唱、听众或发布反馈。
- 可核对的成熟专业机制。

验证必须说明：测试了什么、哪些变量保持不变、结果支持或反驳什么。只因改后更长、更复杂或AI评分更高不构成验证。

通过后从 `candidate` 变成 `validated`；失败则保留证据并废弃或修正根因。

## 模式四：`promote_or_deprecate`

### 晋级为active

需要：

- 明确验证证据。
- 适用边界和反例。
- 与既有记录的冲突检查。
- 用户明确授权长期使用，或项目已有针对该类型的授权。

晋级时优先合并或替换旧记录，不追加近义规则。

### 进入通用knowledge

比个人active更严格：必须证明不是个人偏好、不是单一题材偶然、能够改变跨作品决策，并由用户明确授权。修改通用知识时删除或合并冲突旧内容。

### 废弃

记录为什么失效、由哪个新记录替代。不得删除真实原始证据。

## 模式五：`compile_profile`

`profile.yaml`是带证据来源的当前个人摘要，不是另一套规则库。只汇总active或稳定validated偏好：

```text
dimension
tendency
scope
confidence
evidence_ids
conflicting_evidence_ids
ask_when
```

摘要必须能从记录重建。不得把candidate写成已学会，不得预设新用户偏好。

## 运行时召回

按当前题材、人物关系、阶段、乐段、根因层和决策维度检索。优先：

1. 当前上下文高度相似的active记录。
2. 有跨作品证据的validated记录。
3. 与当前决策直接相关的偏好。

一次只加载少量记录，并把使用ID写入作品状态。若记录没有改变当前决定，不加载。

## 典型错误与纠正

| 错误 | 正确处理 |
|---|---|
| 用户讨厌一次雨景，永久禁用雨 | 追到意象选择和人物感知；保留被重新授权的反例 |
| 用户选择克制副歌，规定所有副歌克制 | 记录题材限定偏好，新题材重新询问 |
| 当前稿未认可，AI先沉淀理论 | 先修稿，等结果认可和沉淀授权 |
| 新反馈与旧规则相似，追加一条 | 修改唯一权威记录并废弃重复 |
| 平台没执行停顿，写成音乐理论 | 先记录平台证据和提示词解析归因 |

## 红线

- 不照抄用户原话冒充可执行规则。
- 不因反馈语气强烈提高证据等级。
- 不把个人偏好写成客观真理。
- 不只记录根因而缺少表面触发证据。
- 不只记录表面禁令而缺少因果链。
- 不把未认可的AI示例写入长期资产。
- 不自动修改其他作品、通用知识或Skill。
- 不全量加载记忆。

## 完成

当前作品问题已被送到正确修改层；反馈类型清楚；根因和表面证据完整；记录状态符合真实证据；晋级权限没有越权；个人profile只引用可追溯记录。
