# 经验材料吸收与本地资产更新闭环

当老胡提供参考歌、歌词文章、创作理论、生成失败样本、听后反馈、发布数据、对某句歌词的评价，或指出项目流程 / 执行文件 / 交付方式 / 评审方式存在问题时，进入本闭环。

```text
原始材料归档
→ 反馈对象识别
→ 判断材料类型
→ 提炼它对音乐创作哪一环有用
→ 做五项测试
→ 判断规则状态
→ 判断进入硬门、执行流程、增强资产还是规则进化
→ 更新作品复盘、共享资产、质量系统或对应 laohu_ skill
→ 在输入输出索引记录
```

## 0. 反馈对象识别

所有反馈进入五项测试前，必须先识别反馈对象。不能默认把老胡反馈当成“给当前歌词加一条规则”。

```text
作品内容反馈：
指向某句歌词、某段副歌、某个选题、某个风格结果。处理重点是当前作品和对应生成 / 修复 skill。

执行能力反馈：
指向某个 skill 本来应该做到但没做到。处理重点是 skill 执行顺序、硬门、停止点和修复动作。

规则分层反馈：
指出规则写错层级，例如把上限技巧写进下限 skill，把具体作词细节写进顶层，把类型化经验写成稳定硬门。处理重点是迁移、降级、删除或改写规则位置。

反馈流程反馈：
指出系统吸收反馈的方式错了，例如只改单文件、只修表象、没做全链路影响扫描、没抽象共性机制。处理重点是更新本闭环、AGENTS、复盘协议或交接流程。

项目结构反馈：
指出目录、文件职责、skill 边界、共享资产边界、顶层职责不清。处理重点是项目结构和文件职责，不是歌词内容。
```

命中“规则分层 / 反馈流程 / 项目结构”时，必须先进入系统修复模式：

```text
1. 暂停继续追加具体作词规则。
2. 说明旧流程为什么导致本次错误。
3. 修改流程入口、文件职责或写入判定规则。
4. 回查刚才是否已有规则写错层级；需要迁移或删除时直接处理。
5. 再判断是否需要更新具体 skill 或共享资产。
6. 回复老胡时说明：下次同类反馈会先经过什么流程，不会再直接改单文件。
```

系统修复完成判定：

```text
有流程入口更新。
有文件职责或写入边界更新。
有错误写入的迁移 / 降级 / 删除检查。
有全链路影响说明。
只改某个 skill 或某条共享资产，不算系统修复完成。
```

材料类型：

- 参考歌 / 优秀歌词：先过高质量样本门，只吸收流传广、受欢迎、专业完成度高或长期验证的成熟作品；拆宏观工艺，不保存大段原文。
- 老胡反馈：提取肯定、否定、原因和长期偏好。
- 生成失败样本：记录失败原因、模型表现、下次如何避免。
- 文章 / 理论：判断进入题眼、曲式、歌词、修词、演唱控制还是复盘规则。
- 发布反馈：记录听众记住哪一句、切片效果、评论区引用、播放和转发。

原则：

- 不只改当前歌词，要改以后怎么写。
- 老胡反馈是训练材料，不是临时抱怨；但也不是绝对真理，必须先被理解、质疑、分类、验证。
- 所有反馈都必须落到文件：对应 skill、共享资产、流程文件、当前作品记录、规则进化备忘录或输入输出索引。不能只在聊天中说“已理解”。
- 失败样本是资产，不是垃圾。
- 长期有效经验必须落到共享资产或 skill。
- 如果老胡指出的是流程、规则、skill、交付格式或判断标准问题，不能只写复盘报告。报告只是中间证据，必须继续判断是否写回共享资产和对应 `laohu_` skill。
- 只有两种情况可以暂缓写回正式规则：老胡明确要求先不要改项目；或该反馈明显只是单次偏好、证据不足、会污染其他类型作品。暂缓时必须在报告里写清“为什么暂缓”和“需要什么证据才能升级”。
- 当老胡追问“项目有没有优化 / 下次还会不会犯”时，必须立即检查并更新对应共享资产、skill 和索引状态，不能只回答已经有报告。
- 当老胡指出“不要只写指标 / 要治本 / 要防下次复发”时，必须把经验写成通用规则、触发条件、错误机制、反例、正例和检查问题。只加评分项、扣分项、禁词表或一句原则，不算完成。

## 五项测试

五项测试前必须先做“底层逻辑提取”。它的目的不是把老胡的话改写得更正式，而是找出这次反馈背后可迁移的错误结构。

```text
1. 表层反馈：老胡这次直接说了什么、否定了什么、追问了什么？
2. 真实表达：他真正想让系统以后避免什么质量损失、体验损失或流程失控？
3. 共同错误结构：同类问题换成别的歌词、题眼、曲式、演唱控制、复盘或文件更新时，会以什么形式出现？
4. 底层破坏点：它破坏人物、关系、逻辑、唱感、传播、阶段门、skill 责任、文件职责还是规则分层？
5. 默认行为改变：下次哪个 skill、流程或共享资产要提前判断、拦截、追问、降级、迁移或删除？
6. 验证问题：以后遇到类似输入时，用哪几个问题检查是否真的吸收了这条经验？
```

只有完成这一步，才能进入五项测试。否则很容易把反馈写成“当前补丁”，看似落文件，实则没有改变系统下次的默认行为。

进入五项测试前，还必须补出“反例 / 正例小样本”：

```text
反例：同类失败写法至少 1 个，并写清楚失败机制。
正例：可迁移的正确方向至少 1 个，并写清楚它靠什么成立。
边界：这个正例不能被机械复刻到哪些场景。
```

反例和正例的作用是校准规则，不是建立固定模板。比如“不要用旧灯光”不是为了永远禁用“旧”或“灯光”，而是为了拦住“用形容词和万能物象假装年代感”的错误；如果某首歌里灯是人物每天关掉、等人回来或守夜的核心动作证据，它仍然可以用。

如果在解释反馈时已经承认当前产物存在硬伤，不能只完成解释。必须立刻闭环：

```text
当前产物：改掉该句或形成明确 writer 修改交接单。
项目经验：写回对应 skill / 共享资产 / 作品复盘。
对老胡：说明改了哪里、写回哪里、下次如何避免。
```

只解释“为什么错”，但不改当前产物、不落规则，判为反馈吸收失败。

```text
真实目标测试：
老胡表面说了什么，真正想解决作品质量、创作体验还是长期系统问题？

事实与逻辑测试：
这条判断是否成立？有没有反例？是否过度概括？是否只是当前案例有效？是否和作词、音乐、叙事、传播、审美规律冲突？

适用边界测试：
它适用于所有歌词、某类题材、某种曲风、某个平台目标，还是某个作品个案？

冲突测试：
它和已有规则是否冲突？哪条更底层、更普适？是否需要覆盖旧规则、降级旧规则，或两条都保留但标注边界？

写入层级测试：
它应该进入 writer skill 硬门区、writer skill 执行流程区、repair skill 诊断 / 修复流程、共享资产库、质量评估与预测系统、案例经验库、当前作品复盘、规则进化备忘录，还是暂不写入？
```

## 规则状态

```text
候选规则：刚从反馈中提炼，还没有经过产出验证。
临时执行规则：先在 1-3 次创作中试用。
稳定规则：多次验证有效，可以写入 skill 本体。
争议规则：有用但有边界，放共享资产并标注适用场景。
淘汰规则：被证明误导创作，应删除、降级或迁出核心执行区。
```

落文件判定：

```text
反馈影响跨风格初稿下限：
必须写入对应 writer skill 硬门。

反馈影响硬门执行顺序：
必须写入对应 writer skill 执行流程或流程文件。

反馈影响诊断、可救判断、修复动作：
必须写入对应 repair / review skill。

writer / structure / sing_control_writer 因老胡反馈新增硬门时：
必须同步检查对应 repair skill 是否已有可检视项。若没有，必须补写 repair 检视规则，让评审官下次在打回 writer 之前就能抓到同类问题。不能只写生成规则，不写评审规则；否则系统会变成“生成者知道不该犯，但评审官不会拦截”，缺陷仍然要靠老胡人工发现。

反馈影响特定题材、流派、词池、名家视角、长案例：
必须写入共享资产或案例经验库。

反馈影响评分、预测、复盘、验证：
必须写入质量评估与预测系统。

反馈影响流程、阶段门、交付格式：
必须写入 02_共享资产库/05_工具流程/。

反馈只影响当前作品：
必须写入当前作品阶段文件、阶段确认记录或复盘。

反馈暂时无法升级：
必须写入规则进化备忘录，标记待验证。
```

吸收完成判定：

```text
只改当前产物，没有提炼共同错误结构和底层破坏点：
只算当前修补，不算经验吸收完成。

只把反馈原话写进文件，没有说明下次默认行为如何改变：
只算记录，不算规则进化完成。

只加指标 / 扣分项 / 禁词表，没有通用规则、错误机制、反例和正例：
只算风险提示，不算治本。

解释出当前产物硬伤，但没有修改当前稿或形成 writer 修改交接单：
只算自我辩解，不算反馈闭环。

有报告但没有规则写回：
只算复盘完成，不算系统优化完成。

共享资产已更新，但执行 skill 没有硬门：
只算规则沉淀，不算执行闭环完成。

writer 新增硬门但 repair 没有对应检查项：
只算半闭环，不算评审闭环完成。必须补齐 repair 的“触发条件 + 错误机制 + 反例 + 正确交接方向 + 检查问题”，让评审报告能在修改前暴露问题。

共享资产、对应 skill、当前作品记录和输入输出索引都已更新：
才算本轮经验吸收完成。

没有任何文件更新：
不算吸收，必须继续处理或明确说明被老胡要求暂不写入。
```
