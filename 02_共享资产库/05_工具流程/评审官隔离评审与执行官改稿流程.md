# 评审官隔离评审与执行官改稿流程

本文件定义老胡音乐项目里“初稿 → 多评审官隔离评审 → 执行官汇总取舍 → 优化后终稿”的工作流。

它解决的问题是：歌词优化、style prompt 和演唱控制不能只停在“指出问题”。真正有价值的优化阶段必须产出可直接使用的优化后结果。

## 0. 创作中枢先于流程表

评审流程不能把音乐创作变成表格工程。所有评审、裁决和改稿都先围绕同一个创作中枢：

```text
这首歌替谁唱？
他在什么场景里痛？
他最想说但说不出口的是哪句话？
副歌能不能让这个人认账？
这句话能不能唱、能不能记、能不能传播？
```

评审输入包先给作品本身，再给必要背景。执行官输出先给改后的方向、歌词或演唱控制，再给评审归因和 Agent 记录。Agent 记录、裁决表、交接字段用于证明流程闭环，不得抢在作品前面成为主产物。

评审官不需要看 `故事杠杆、金句钉、损失厌恶、共鸣网、利他金、英雄之旅` 等项目术语。执行官可以在评审后做归因，但对老胡展示时必须翻译成人话。

## 1. 根本目的

```text
初稿不是终稿
评审不是终点
建议必须进入执行
执行后必须形成可投喂 / 可确认的最终版本
```

## 1.1 使用边界：探索阶段先自审，正式三阶段默认多评审

本流程服务统一创作链里的正式生产、正式优化和需要文件闭环的阶段，不要在灵感初聊、方向探索、歌词基础水平测试时提前启动完整评审框架。

输入状态还轻、核心字段未确认时，默认只做“生成后反向审稿”：

```text
把自己刚写的内容当成别人写的稿子挑毛病。
发现问题后直接改正文。
对老胡只展示改后的结果和极短说明。
不输出评审官名单、裁决表、Agent 记录和完整交接字段。
```

同一条创作链进入正式三阶段质量小循环后，默认启用真实独立 Agent / sub-agent 评审：

```text
老胡明确说交给评审官、正式制作、歌词优化、演唱控制优化、发布包装或复盘沉淀。
老胡要求从灵感到最终投喂版、一步到位、完整制作或工程化生产。
当前作品已有确认题眼、副歌核心句、曲式或完整歌词，需要多角色审美纠偏。
```

评审不是为了证明流程跑过，而是为了发现同一上下文看不见的假、人味不足、唱感失败、规则味和制作风险。若只是想给老胡看一个初步方向，先自审改稿，不要把创作现场变成评审报告。

评审官和执行官都必须额外检查四类新风险：

```text
普通话冒充歌词：逻辑顺，但没有气口、尾音、韵脚和乐段位置。
弱虚尾：关键句尾落在了 / 啊 / 呢 / 吧 / 嘛，撑不起情绪上升。
道具堆叠：物件很多，但没有动作、关系、代价和情绪功能。
压缩词外露：用“认账、题眼、故事杠杆”等内部词替代真实听众反应。
```

对老胡展示评审结论时，不说“这句认账感不足”，要说“这句还没有替那个人把没说出口的话说出来”。不说“物象无魂”，要指出哪个物件只是摆设、删掉后情绪并不会变弱。

适用阶段：

- 选题题眼：由 `laohu_music_topic_writer` 生成或修改选题规划，由 `laohu_music_topic_repair` 负责选题评审诊断、量化评分和 writer 修改交接单。
- 歌词优化：由 `laohu_lyrics_repair` 作为执行官。
- 最终 style prompt 与演唱控制优化：由 `laohu_sing_control_writer` 生成初稿和执行修改，由 `laohu_sing_control_repair` 负责声音评审诊断、量化评分和 writer 修改交接单。
- 必要时也可用于曲式与风格方案复查，但默认不新增单独阶段。

## 2. 角色定义

### 2.1 评审官

评审官不是普通“视角调用卡”。评审官必须独立看稿、独立挑错、独立给改法。

评审官也不是规则验收员。评审官不得被要求按项目生成规则逐条打勾，不得接收大段 `laohu_*` 规则清单，不得把“是否满足规则”当成主要判断。评审官的唯一目标是用真实人类审美判断作品是否成立：

```text
像不像歌。
像不像人写的。
能不能唱。
有没有一句真的扎人。
有没有 AI 味、作文味、规则味、模板味。
如果我是听众，会不会记住、转发、复听或认账。
如果我是制作人，这个歌词 / prompt / controlled lyrics 会不会生成出对的音乐。
```

规则只属于执行官。执行官在评审后负责把评审官的直觉病灶翻译成：题眼问题、歌词问题、韵脚问题、乐段问题、风格问题、演唱控制问题或系统规则问题。不能把这一步倒过来，让评审官先按规则说话。

评审官来源：

- `02_共享资产库/05_工具流程/外部创作者视角调用表.md`

每个评审官只带一个宽泛审美入口，不领取项目规则清单。入口用于激发不同人类判断，不用于逐条验收，例如：

```text
方文山评审官：这份国风语感是否像歌，还是像堆古典符号。
林夕评审官：心理矛盾是否像真人的执念，还是像解释情绪。
黄伟文评审官：角度和锋芒是否有记忆点，还是太乖太安全。
李宗盛评审官：人味和人生代价是否真实，还是像作文感想。
字词语感评审官：只看字、词、短语和句子搭配，找出语义能解释但公共语感不成立的选字、组词和造句。
Max Martin评审官：副歌是否让人想跟唱，还是只完成了结构。
Rick Rubin评审官：哪些聪明、装饰和控制其实应该删掉。
FINNEAS评审官：声音是否贴耳、有留白，还是把情绪做满做假。
陈奕迅评审官：口气、停顿和尾音是否可信，还是不像人在唱。
```

歌词阶段必须额外加入“字词语感评审官”。这个评审官不是规则验收员，也不评价整首歌是否高级，只负责微观语言病：

```text
选字是否准确，而不是语义相近。
组词是否是公共搭配，而不是作者临时硬组。
动宾关系是否自然，例如到底是谁对谁做了什么。
单字是否承重过多，例如亮、轻、低、白、空、远、软、淡、小、冷、满、深等字同时承担画面、情绪、关系和押韵。
句子是否第一耳像人会唱出来的话，而不是解释后才能成立。
为了押韵、古风、修辞、金句或压缩，是否牺牲了自然汉语。
```

它的输出格式要短而准：`原词 / 原句 → 问题类型 → 为什么第一耳不自然 → 建议 writer 往哪类词或动作修`。它不直接给完整改句，不负责打最终分。

### 2.2 诊断官 / 执行官

诊断官负责汇总评审意见，但不能机械照单全收。评审官给的是人的判断，诊断官给的是规则归因、量化评分和 writer 交接。

诊断官必须读取本阶段对应 repair skill 和质量 rubric，再处理评审官意见：

```text
选题阶段：laohu_music_topic_repair + 音乐作品质量 rubric 选题规划评分。
歌词阶段：laohu_lyrics_repair + 音乐作品质量 rubric 歌词评分。
演唱控制阶段：laohu_sing_control_repair + 音乐作品质量 rubric 演唱控制评分。
```

诊断官要做四件事：

```text
1. 归因：判断评审官指出的问题对应人物、题眼、歌词、韵脚、乐段、风格、人声、生成稳定性还是流程问题。
2. 裁决：区分多位评审官的共识、少数有效意见、个人口味和误判。
3. 打分：按对应 repair skill 和 rubric 给出证据链评分，不让评审官直接打规则分。
4. 交接：把成立的问题转成 writer 下一轮必须修、必须保留、禁止路线和优先级。
```

在交接给 writer 之前，诊断官还必须完成规则归因与写回门：

```text
评审缺点：
为什么评审官会提出这个问题：
writer 旧规则哪里没拦住：
本轮要新增 / 修正的 writer 规则：
写入位置：
规则状态：稳定规则 / 临时执行规则 / 候选规则 / 当前作品偏好 / 淘汰旧规则
writer 改稿前自检问题：
```

诊断官做规则归因时，歌词阶段和选题阶段必须额外识别三类高频病灶：

```text
安全叙事 / 中性词过载：评审官说“太顺、太温、没有刺、像讲故事、画面有但没情绪”时，先检查是否全篇依赖中性物件和温和动作，缺少公共强词、强虚词、关系判词和不可逆决定。
公共强词缺失：评审官说“字没有情绪、词不刁、不像成熟作词人”时，先检查是否没有从公共语感里的熟语、成语、强虚词、关系判词和题材适配抽象词中借势，而是在临时组合安全词。
副歌未升维：评审官说“副歌没打中、传播弱、还在讲事”时，先检查副歌是否仍停在动作、场景、表白或主题态度，没有升成判词、质问、宣告、愿望、认账、公开立场或不可逆决定。
```

这三类问题的交接单不能写成“加强情绪 / 更有文学性 / 更有画面”。必须写成：本轮要刺中的情绪刀口是什么；可借势的公共强词、强虚词或关系判词方向是什么；哪些物件和动作只保留为证据；副歌要采用哪种升维方式；哪些安全叙事路径禁止继续使用。

可复用缺陷写入对应 writer skill、repair skill 或共享资产；只适用于当前作品的，写入本阶段诊断单的临时执行规则；证据不足但可能复用的，写入待验证经验。没有这张规则归因卡，writer 只能得到“改哪里”的意见，不能得到“下一轮按什么新规则改”的约束，本轮不能进入正式改稿。

歌词优化执行官：

```text
laohu_lyrics_repair
```

声音执行官：

```text
laohu_sing_control_repair
```

执行官必须判断：

- 哪些建议采纳。
- 哪些建议只局部采纳。
- 哪些建议拒绝。
- 为什么拒绝。
- 最终结果具体改了哪里。

选题评审诊断：

```text
laohu_music_topic_repair
```

laohu_music_topic_repair 负责判断选题规划哪里空、哪里同质、哪里视角混乱、哪里乐段重复，并输出评分表、核心缺点和给 writer 的修改交接单；不直接输出最终方向、确认题眼、副歌核心句候选和下游交接字段。

## 3. 隔离评审规则

正式三阶段质量小循环默认启动真实独立 Agent / sub-agent 评审；当前环境只担任诊断官，不再把“自己按 repair 标准打分”当作正式评审默认值。任何同一上下文角色扮演、顺序模拟、隔离轮次模拟，都不得计入正式隔离评审。

当前环境可以做诊断模式，但边界必须写清：

```text
灵感初聊、临时自检、单句讨论、早期探索：可以当前环境诊断。
正式选题规划、正式歌词优化、正式演唱控制：必须独立评审官先给评价，再由诊断官归因打分。
诊断模式可以输出问题和参考分，不能写成正式评审通过，不能作为进入下一阶段的依据。
```

完整评审的最低技术门槛：

```text
每位评审官 = 一个独立 Agent 调用。
每个 Agent 只收到同一份待评审输入包 + 自己的评审职责。
每个 Agent 不接收其他评审官意见、执行官预设结论或汇总判断。
执行官必须在所有 Agent 输出完成后才汇总。
阶段文件必须记录 Agent 调用记录。
```

Agent 生命周期也属于正式评审硬门。每个隔离 Agent 返回完成、报错、断流、被替换或确认不再需要后，执行官必须立刻完成三步：

```text
1. 读取结果：完成状态要摘录评分、核心意见和交接单；报错 / 断流要记录失败原因，并标明不计入正式评审。
2. 关闭释放：调用关闭动作释放该 Agent，避免占用并发资源和污染后续评审状态。
3. 写入记录：阶段文件的 Agent 调用记录必须写明 Agent 标识、返回状态、是否计入正式评审、关闭释放状态。
```

已完成但未关闭的 Agent，不得继续复用来做新阶段评审；新阶段必须重新开新的独立 Agent。若发现历史 Agent 未关闭，先关闭释放，再继续当前流程。最终交付前必须确认本轮打开过的评审 Agent 都已完成关闭或记录为仍在等待，不得把资源清理留给下一轮。

如果当前环境没有可用 Agent / sub-agent 工具：

```text
可以输出“当前环境诊断模式”或“待隔离评审输入包”。
不能写成“评审官隔离意见摘要”。
不能输出“完整评审已完成”。
不能进入“隔离评审通过”名义。
不能把同一上下文里的角色扮演当作隔离评审。
即使当前环境诊断达到阶段分数门槛，也不能当作正式三阶段通过；必须等真实 Agent 返回后由诊断官重新归因、打分和裁决。
```

智能体硬门：

```text
没有开智能体 = 正式隔离评审未完成；当前环境最多只能完成诊断模式。
智能体未返回 = 隔离评审未完成。
只有一个智能体返回但规则要求多评审官 = 只能标记为部分评审，不得进入下一阶段。
同一上下文模拟 = 不计入智能体评审。
“一步到位” = 只跳过老胡中途确认，不跳过智能体评审。
```

执行官只有在满足本阶段最低 Agent 数量和返回要求后，才能做正式汇总、改稿、裁决或交接。否则必须停在待评审输入包 / 草案 / 诊断模式。

每个评审官只能收到同一份最小必要材料：

```text
作品目标：
题眼：
副歌核心句：
主风格 / 曲式：
待评审初稿：
完整确认歌词：
该评审官宽泛审美目标：
该评审官禁止事项：
输出格式：
```

如果评审对象是最终 style prompt 与演唱控制，“待评审初稿”不能只是一段自然语言声音描述，必须同时包含：

```text
初稿 style prompt：
完整确认歌词：
初稿 controlled lyrics：
演唱控制符号说明：
  [] 表示段落级控制，只控制当前乐段，放在乐段开头。
  [()] 表示关键行控制，只控制它下面紧跟的一句歌词，单独成行。
本轮希望评审官判断：
  这份声音设计是否真的服务歌词。
  听起来会不会生成成模板歌、晚会歌、宣传片、过度煽情或无效高级。
  哪些声音词、段落控制或行级控制最假、最挡歌词、最容易带偏模型。
  哪些地方只需要说人话，不需要堆控制。
```

声音评审官必须在看过完整确认歌词、完整初稿 style prompt 和完整初稿 controlled lyrics 后再评审。只看 style prompt、只看自然语言说明、只看 controlled lyrics 摘要，或只看几处标签的声音评审，不能算完整演唱控制评审。

如果评审对象是选题题眼，“待评审初稿”必须包含三个完整方向，而不是三个标题或三句口号：

```text
原始灵感：
初稿方向 A / B / C：
每个方向的嘴替对象：
明确人群：
具体场景：
核心关系：
情绪债务：
故事引擎：
证据配额：
题眼判断：
副歌核心句候选：
不建议走的方向：
```

选题评审官只需要像真实内容创作者和听众一样判断：哪个方向最像一首值得写的歌，哪个方向最普通、最假、最像 AI 平均选题，哪个方向之外还有没有更像人的真实切口。不要让选题评审官逐条检查题眼公式、故事杠杆、英雄之旅或其他生成字段。

禁止给评审官看到：

- 其他评审官的意见。
- 执行官的预设结论。
- 其他评审官的改句。
- 与其职责无关的大量项目上下文。

原因：

```text
评审官之间必须互不污染。
每份意见要保留独立审美判断。
碰撞应该发生在执行官汇总阶段，而不是评审官互相模仿阶段。
```

### 3.1 Agent 调用记录硬门

阶段主文件必须包含一段 `Agent 调用记录`，用于证明本轮不是上下文模拟：

```text
Agent 调用记录：
评审官：
Agent 标识：
发送输入包内容：
完整确认歌词：已发送 / 未发送
完整初稿 style prompt：已发送 / 未发送
完整初稿 controlled lyrics：已发送 / 未发送
符号说明：已发送 / 未发送
是否包含其他评审官意见：否
是否包含执行官预设结论：否
返回摘要位置：
是否纳入 repair 诊断：是 / 否，原因：
```

没有 Agent 调用记录时，本阶段只能算“草案 / 诊断”，不能算完整评审，不能进入下一阶段。

## 4. 评审官输出格式

评审官不是“礼貌建议生成器”，也不是规则验收员。评审官要像一位真实的人类创作者、听众、制作人或刀口很准的老师：话可以尖锐，但必须扎中病灶；判断可以刻薄，但必须给证据和可替换方向。评审官不需要使用项目术语，不需要证明自己懂规则，不需要把问题归类成系统字段。

评审语言目标：

```text
一针见血
少说废话
先指出病灶
再给证据
再讲直觉原因
再给可执行改法
最后给一句人话建议
```

每个评审官使用宽格式输出，允许自然语言判断，不强制规则化表格：

```text
评审官：
总体判断：
第一反应：
最不像人 / 最不像歌 / 最像 AI 的地方：
最值得保留的一句或一个方向：
最该删掉或重写的地方：
为什么它不打动人：
如果你来改，会往哪个方向改：
可直接替换的句子 / 题眼 / 声音描述：
一句人话建议：
```

要求：

- 必须说人话，不能只说“更高级”“更有画面”“更有情绪”。
- 必须指出至少 1 个具体病灶，病灶可以是“不像人”“不像歌”“像规则作文”“像 AI 平均句”“像为了押韵而押韵”“像制作标签遮住歌词”。
- 必须给出至少 1 个可直接执行的改法，改法可以是可替换句、可替换题眼、可替换声音描述或明确删法。
- 必须指出至少 1 个可保留点，避免全盘否定导致作品散掉。
- 可以用直觉、经验和审美判断，不要求套用韵脚原理、故事推进、人物声口、传播 hook 或平台生成稳定性等项目术语。
- 如果没有问题，必须说明“为什么它像歌、像人、可唱、可记”。

执行官补充要求：

```text
评审官输出后，执行官再做规则归因。
执行官需要判断评审意见对应的是题眼、歌词、人味、歌感、韵脚、段落、风格、演唱控制、生成稳定性还是系统流程问题。
执行官不得要求评审官先完成这些归因。
```

## 5. 歌词优化执行流程

默认管线：

```text
歌词初稿
→ 选择 3-5 位歌词评审官
→ 每位评审官隔离评审
→ 执行官汇总冲突
→ 形成修改决策表
→ 输出优化后最终歌词
→ 整理给演唱控制阶段的确认歌词
```

歌词优化阶段最终文件必须包含以下材料，但对老胡展示时必须先放“优化后最终歌词”。Agent 记录、评审摘要、裁决表和审计表放在歌词之后，作为证据和归档，不得压过作品：

```text
歌词初稿引用：
Agent 调用记录：
评审官名单：
评审官隔离意见摘要：
执行官修改决策表：
优化后最终歌词：
副歌韵脚审计：
唱感 / 韵母发声审计：
与初稿相比改了什么：
未采纳建议及原因：
给演唱控制的交接字段：
```

硬门：

- 没有“优化后最终歌词”，歌词优化阶段不算完成。
- 如果优化后最终歌词与初稿完全一致，必须说明原因；否则视为执行官没有工作。
- 如果只输出修改建议，不输出终稿，必须明确标记为“诊断模式”，不能标记为完整歌词优化。

默认管线：

```text
选题方向初稿（三个方向）
→ 选择 3-7 位选题角度评审官
→ 每位评审官隔离评审

```

选题阶段文件必须包含以下材料，但对老胡展示时必须先放“修改后选题规划”和“修改后的题眼 / 歌名 / 副歌规划方向”。评审输入包、Agent 记录、评分表和诊断交接单放在后面，作为证据和归档：

```text
选题方向初稿：
选题评审输入包：
Agent 调用记录：
评审官名单：
评审官隔离意见摘要：
量化评分表：
核心缺点诊断：
选题 writer 规则归因与写回卡：
给 laohu_music_topic_writer 的修改交接单：
修改后选题规划：

```

硬门：

- 没有三个完整初稿方向，不能进入评审。
- 没有 repair 量化评分和 writer 修改后规划，选题规划优化闭环不算完成。
- 如果三个方向都被评审为普通，repair 只能指出普通的证据和重构方向，具体重构由 writer 执行。
- 如果只输出评审建议，不输出评分表和 writer 交接单，必须标记为“不完整诊断”，不能标记为完整选题评审。

## 6. Style Prompt 与演唱控制优化流程

默认管线：

```text
演唱控制初稿（初稿 style prompt + 初稿 controlled lyrics）
→ 选择 3-5 位声音 / 制作 / 演唱评审官
→ 每位评审官隔离评审
→ laohu_sing_control_repair 汇总缺点、归因、打分
→ 完成演唱控制 writer 规则归因与写回门
→ 形成 writer 修改交接单
→ laohu_sing_control_writer 按诊断修改 style prompt
→ laohu_sing_control_writer 按诊断修改 controlled lyrics
```

演唱控制阶段最终文件必须包含以下材料，但对老胡展示时必须先放“修改后 style prompt”和“修改后 controlled lyrics”。Agent 记录、评审摘要、量化评分和诊断交接单放在后面，作为证据和归档：

```text
演唱控制初稿：
Agent 调用记录：
评审官名单：
评审官隔离意见摘要：
量化评分表：
核心缺点诊断：
演唱控制 writer 规则归因与写回卡：
给 laohu_sing_control_writer 的修改交接单：
修改后 style prompt：
修改后 controlled lyrics：
关键行控制变化：
修改对应解决的评分短板：
validation：
```

硬门：

- 没有 repair 量化评分和 writer 修改后文本，演唱控制优化闭环不算完成。
- 如果修改后版本与初稿完全一致，必须说明哪些扣分项不需要改；否则视为优化无效。
- 声音评审和 repair 不能改歌词正文，也不能直接输出改后投喂文本；只能改声音策略诊断、评分和交接任务。
- writer 执行修改时只能改 prompt、section notes、key line notes、动态、空间、和声和正向边界，不改歌词正文。

### 6.1 演唱控制评审输入硬门

声音评审官收到的初稿必须已经是“可投喂形态的初稿”，而不是普通文字说明。

必须包含：

```text
1. 初稿 style prompt。
2. 完整确认歌词。
3. 初稿 controlled lyrics。
4. [] 和 [()] 的符号语义说明。
5. 需要评审官判断的控制动作：新增、删除、修改、移动、降级、保留。
6. 禁止评审官改歌词正文的提醒。
7. 段落控制目标格式：`[Section ｜ phrase｜ phrase ｜ phrase]`。
```

符号语义：

```text
[]：
段落级控制。只控制当前乐段整体的编曲、动态、人声距离、情绪和空间，放在乐段开头。
正式输出使用精简短语格式，例如：
[Final Chorus ｜ warm lift｜ restrained low strings ｜ soft harmony tail]

[()]：
关键行控制。只控制它下面紧跟的一句歌词，单独成行，用于 hook、转折、暴露句、传播锚点和尾句。
行级控制可以使用自然语言短句，但必须偏演唱技法和声音动作，不写长段说明。
```

无效评审：

```text
只评 style prompt，不评 controlled lyrics。
只给确认歌词或 controlled lyrics 摘要，不给完整正文。
只评自然语言声音方向，不评 [] / [()] 是否有效。
终版出现大量 [] / [()]，但评审阶段没有评审这些标签。
评审官不知道 [] 和 [()] 的控制范围。
评审不是独立 Agent 返回，而是在同一上下文里模拟。
```

## 7. 冲突处理

评审官意见冲突时，执行官按以下优先级裁决：

```text
题眼一致性
副歌核心句传播力
可唱性
生成可用性
老胡明确偏好
单个评审官的个人风格
```

常见冲突：

```text
林夕要求更复杂，Max Martin要求更短：
优先保留副歌短 hook，把复杂心理放到 Verse / Bridge。

方文山要求意象更密，李宗盛要求更像人话：
如果不是国风题材，优先李宗盛；如果是国风题材，保留意象但必须可唱。

Rick Rubin要求删，Adele / 张惠妹要求爆发：
先判断作品任务。倾诉型优先删，释放型保留爆发但限制段落。

FINNEAS要求留白，Hans Zimmer要求堆叠：
私密叙事优先留白，电影感作品才允许堆叠。
```

## 8. 评审反哺初稿 Skill 的进化闭环

评审官找出缺点不是流程的终点。真正的目标是让下一次初稿少犯同类错误。

每次完整评审后，执行官必须在 writer 改稿前追加一张“初稿缺陷归因与 Skill 进化卡”。这不是最终复盘附件，而是改稿前的硬门；没有它，writer 不得直接按旧规则重写。

```text
本轮被评审找出的核心缺陷：
缺陷证据来自哪些 Agent：
为什么评审官会提出这些问题：
真实目标测试：
事实与逻辑测试：
适用边界测试：
冲突测试：
写入层级测试：
规则状态：候选规则 / 临时执行规则 / 稳定规则 / 争议规则 / 淘汰规则
缺陷来自哪个初稿生成环节：
  选题题眼 / 曲式风格 / 歌词初稿 / 演唱控制初稿 / 交接字段 / 共享资产缺口
为什么初稿 skill 当时没有避免这个问题：
  缺少规则 / 规则太弱 / 规则有但没有硬门 / 交接字段缺失 / 评审视角没有前置
本轮新增 / 修正的 writer 规则：
应该写回哪里：
  skills/laohu_music_topic_writer/SKILL.md
  skills/laohu_lyrics_writer/SKILL.md
  skills/laohu_sing_control_writer/SKILL.md
  skills/laohu_music_topic_repair/SKILL.md
  skills/laohu_lyrics_repair/SKILL.md
  skills/laohu_sing_control_repair/SKILL.md
  02_共享资产库/02_音乐语言资产/...
  02_共享资产库/05_工具流程/...
  02_共享资产库/03_质量评估与预测系统/规则进化备忘录.md
本轮已经写回什么：
下次出初稿前必须新增的自检问题：
仍需后续验证的假设：
```

写回原则：

- 如果是明确执行错误或硬质量门缺失，且通过事实逻辑、适用边界和冲突测试，必须当轮改对应 skill 或流程文件。
- 如果只是单次审美偏好，写入当前作品复盘，不直接升级成通用规则。
- 如果可能跨作品复用但证据不足，写入规则进化备忘录，后续作品主动验证。
- 如果同类缺陷反复出现，必须从备忘录升级到正式 skill 或共享资产。
- 如果规则有用但边界明显，写入共享资产或类型化经验，标为争议规则，不得挤进 writer 基础能力内核。
- 如果旧规则被证明误导创作，必须提出删除、降级或迁出核心执行区，并写入淘汰规则记录。

歌词阶段的默认反哺对象：

```text
laohu_lyrics_repair 发现的问题
→ 归因到 laohu_lyrics_writer 的初稿生成规则
→ 必要时同步加厚题眼、韵脚、唱感或画面资产共享规则
```

演唱控制阶段的默认反哺对象：

```text
laohu_sing_control_repair 评审发现的问题
→ 归因到 laohu_sing_control_writer 的初稿生成规则
→ 必要时同步加厚演唱控制与 style prompt 专项规则
```

选题阶段的默认反哺对象：

```text
laohu_music_topic_repair 评审发现的问题
→ 归因到 laohu_music_topic_writer 的初稿方向生成规则
→ 必要时同步加厚题眼与副歌核心句规则或类型化评审经验库
```

硬门：

- 只有“评审建议”和“执行官终稿”，没有“为什么初稿会犯错”的归因，本轮进化不完整。
- 只有归因但没有五项测试、规则状态和写回 skill / 共享资产 / 备忘录，本轮进化不完整，也不能打回 writer 正式改稿。
- 只写 writer 修改交接单，没有新增 / 修正规则或本轮临时执行规则，writer 不得开始重写；否则会继续沿用旧规则。
- 不能把所有问题都留到最终复盘；明确的流程缺口必须即时写回。

## 9. 文件规则

默认不为每个评审官单独创建作品文件。

评审官意见写入当前阶段主文件即可：

```text
04_歌词优化/文本/yyyy-mm-dd_歌词优化与最终歌词.md
05_演唱控制/文本/yyyy-mm-dd_最终style_prompt与演唱控制.md
```

只有在以下情况才允许保存独立评审日志：

- 老胡明确要求保留评审全过程。
- 自动化批量运行需要审计。
- 本轮评审结论会作为长期案例沉淀。

如需保存，放入：

```text
04_诊断与系统日志/
```

不要污染作品阶段目录。
